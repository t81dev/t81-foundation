# 第 13 章：对抗建模与确定性攻击

## 13.1 威胁模型

**状态：理论性**

T81 假设存在一个敌对环境。**宿主**（操作系统、硬件、操作员）被视为可能试图进行以下操作的对手：
1.  **引入熵**：将随机性注入确定性执行中。
2.  **伪造状态**：声称计算达到了状态 $S'$，而实际上达到了 $S$。
3.  **拒绝服务**：消耗无限资源。
4.  **泄露信息**：通过侧信道暴露私有数据。

## 13.2 编译器级攻击

**攻击向量**：“特洛伊源码” / 同形异义字。
**描述**：攻击者使用 Unicode 控制字符（例如，从右到左覆盖）使源代码在人类看来与编译器看来不同。
**缓解**：T81 词法分析器强制执行 UTF-8 的严格子集。在标记化过程中拒绝控制字符和不可打印字符。

**攻击向量**：令牌重排序 / 优化漂移。
**描述**：恶意编译器可能会以在一种架构上保留语义但在另一种架构上不保留语义的方式重新排序指令（例如，由于内存模型差异）。
**缓解**：T81 编译器生成 **规范 AST**。IR 生成阶段是确定性且与平台无关的。`t81lang_repro_gate` 验证编译器输出在不同运行之间是位完全相同的。

## 13.3 VM 和 GC 攻击向量

**攻击向量**：Rowhammer / 比特翻转。
**描述**：针对 DRAM 的物理攻击，翻转敏感内存中的比特（例如，将 `Deny` 裁决更改为 `Allow`）。
**缓解**：T81 使用 **不透明句柄** 和 **内存分段**。关键内核结构存储在隔离页面中（如果可能）并通过校验和进行验证。然而，没有 ECC 内存，软件无法完全缓解硬件故障。

**攻击向量**：垃圾回收非确定性。
**描述**：如果 GC 基于挂钟时间或内存压力运行，则执行追踪将在不同运行之间出现分歧。
**缓解**：T81 GC 是 **确定性的**。它仅由分配计数触发 (`bytes_allocated > threshold`)。这确保了 GC 暂停在每次运行的完全相同的指令处发生。

**攻击向量**：计时侧信道。
**描述**：观察计算函数（例如，模幂运算）所需的时间以推断密钥。
**缓解**：`dmath` 旨在为加密原语提供恒定时间实现，但通用算术不保证是恒定时间的。T81 侧重于 *功能* 确定性，而不是 *时间* 确定性（恒定周期）。

## 13.4 CanonFS 和哈希攻击

**攻击向量**：哈希碰撞 / 原像。
**描述**：找到两个不同的输入 $A \neq B$ 使得 $Hash(A) = Hash(B)$。
**缓解**：T81 使用 **SHA3-256** (Keccak)，它对长度扩展攻击和碰撞攻击具有抵抗力。规范序列化规则（排序键、规范化浮点数）通过减少有效对象的输入空间来最小化攻击面。

## 13.5 分布式层时间旅行攻击

**攻击向量**：状态扣留 / 重放。
**描述**：在第 4 层，一个节点计算状态转换 $S_t \to S_{t+1}$ 但将其扣留，稍后释放以使其他节点的工作无效（类似于“自私挖矿”）。
**缓解**：
1.  **Lamport 时间戳**：每个转换必须因果地跟随前一个转换。
2.  **共识法定人数**：状态只有在由认知集群的 $2/3$ 签名后才最终确定。
3.  **追踪合并**：如果分支出现分歧，确定性合并函数将根据总计算工作量（追踪长度）解决冲突。

## 13.6 确定性破坏事后分析模板

**状态：流程**

如果检测到确定性破坏（即 `t81lang_repro_gate` 失败），则调用以下程序：

1.  **隔离**：识别分歧输入以及追踪 $A$ 与追踪 $B$ 不同的具体指令索引。
2.  **重现**：创建一个最小重现案例 (`repro.t81`)。
3.  **分析**：
    *   是编译器错误吗？（检查 AST 转储）
    *   是 VM 错误吗？（检查 `dmath` 实现）
    *   是主机库问题吗？（检查 `libc` 链接）
4.  **补救**：
    *   修补 `dmath` 以替换主机回退。
    *   使用新的回归测试更新 `t81lang_repro_gate`。
5.  **披露**：发布“确定性公告”（如果生产系统受到影响）。
