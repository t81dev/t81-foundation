**T81 — это тройная операционная система для искусственного интеллекта.**

Каждая загружаемая вами модель работает в управляемой детерминированной среде выполнения. Ядро Axion перехватывает каждую операцию ИИ до того, как возникнет какой-либо побочный эффект. Файловая система является адресованной по содержимому и неизменяемой. ISA заменяет matmul с плавающей запятой на сложение — модуль умножения не требуется. Здесь работает любой ИИ, выражаемый в троичных весах: проверяемо, воспроизводимо и под явным политическим контролем.

```sh
curl -fsSL https://github.com/t81dev/t81-foundation/releases/latest/download/install.sh | sh
```

## ОС, которой не хватало AI

Бинарные операционные системы предоставляют агентам ИИ слот процесса и файловую систему. Вот и все. Они не могут сказать вам, был ли вывод точным по битам, какая политика разрешила загрузку модели или были ли веса на диске теми весами, которые выполнялись. T81 закрывает этот пробел — не путем наложения инструментов поверх существующей ОС, а путем создания ядра, ISA, файловой системы и модели процессов, необходимых для вычислений с использованием искусственного интеллекта.

### 1. Ядро, которое управляет каждой операцией ИИ до появления побочных эффектов.

Когда сегодня агент ИИ предпринимает действие, обычно не существует механизма, позволяющего проверить *постфактум*, что он вычислил, какую политику применил или был ли изменен результат. T81 исправляет это на уровне инструкций.

Ядро **Axion** перехватывает `AgentInvoke`, вызовы FFI и каждый код операции вывода в TISC ISA *до того, как возникнет какой-либо побочный эффект*. Политика написана на языке политик Axion (APL) и является аварийно-закрытой — сбой анализа политики останавливает операцию. Каждое перехваченное событие записывается в журнал аудита, привязанный к **CanonFS**, который можно детерминированно воспроизвести.

```apl
# secure_model.apl — allow inference only for verified model hashes
allow infer if model.hash in approved_models;
deny  infer reason "unapproved-model";
```

```sh
t81 code run inference.t81 --policy secure_model.apl
# Axion: ALLOW  infer  model=sha3:a3f7c2b1…
# Axion: DENY   infer  model=sha3:deadbeef…  reason=unapproved-model
```

### 2. Воспроизводимость как инвариант ядра, а не инструментальная дисциплина

IEEE 754 с плавающей запятой по своей природе чувствителен к платформе: различаются режимы округления, меняется ненормальная обработка, изменяется доступность FMA. Рабочие нагрузки ИИ, построенные на его основе, не могут быть с уверенностью воспроизведены или проверены.

Сбалансированная троичная арифметика симметрична относительно нуля. Округление — это усечение — никакого смещения направления, никакого смещения в зависимости от платформы. Детерминированные поверхности T81 создают **хэши трассировки CanonHash81, которые побитно идентичны** на всех поддерживаемых платформах и проверяются при каждом запуске CI. Это не та собственность, которую можно закрепить; это следствие конструкции ISA.

```sh
t81 determinism verify-run program.tisc
#  Run 1: a3f7c2b1e94d8f20…
#  Run 2: a3f7c2b1e94d8f20…
#  ✓  bit-exact match confirmed
```

Проверенные платформы: **Linux x86\_64**, **macOS ARM64**. Любое расхождение на управляемой детерминированной поверхности рассматривается как критический дефект.

### 3. ISA поддерживает троичные веса — единица умножения не требуется

Тройные веса {−1, 0, +1} не имеют дробной составляющей. Скалярное произведение над ними представляет собой серию условных операций сложения/вычитания – умножение не требуется. T81 предоставляет шесть опкодов TISC, которые напрямую используют это:

| Код операции | Операция |
| :--- | :--- |
| `TWMATMUL` | Умножение троичной весовой матрицы |
| `TQUANT` | Квантовать активации в трит |
| `TATTN` | Троичное внимание (Q · Kᵀ по весам тритов) |
| `TWEMBED` | Поиск по встраиванию веса |
| `TERNACCUM` | Накопление скалярного трит скалярного произведения |
| `TACT` | Активация с помощью потолочных ворот Axion |

Это соответствует моделям класса BitNet b1.58/xTern: **снижение энергопотребления в 15–60 раз**, **прирост пропускной способности в 4–90 раз** по сравнению с базовыми показателями FP16/FP32 при сопоставимой точности. T81 Формат Ternary Weight (T81WTN) хранит квантованные модели; `t81 weights import` преобразуется из SafeTensors или GGUF.

```sh
t81 weights import model.safetensors -o model.t81w
t81 code run inference.t81 --weights-model model.t81w --policy secure_model.apl
```

## Архитектура

T81 — это ОС. Каждый компонент имеет аналог в традиционном дизайне ОС, созданный с нуля для троичной семантики и собственных рабочих нагрузок искусственного интеллекта.

| T81 компонент | аналог ОС | Роль |
| :--- | :--- | :--- |
| **TISC ОДИН** | Набор инструкций (RISC-V, ARM) | Контракт замороженного исполнения; все программное обеспечение компилируется под него |
| **T81VM** | Механизм выполнения ядра | Детерминированный интерпретатор TISC; Axion срабатывает при каждом коде операции |
| **Axion** | Ядро безопасности | Политика аварийного закрытия до появления каждого побочного эффекта; привязанный к аудиту |
| **CanonFS** | Файловая система | Контентно-адресованный, неизменяемый; веса моделей проверены хэшем |
| **T81Язык** | Язык системного программирования | Компилируется в TISC; `agent`/`behavior` — модель процесса |
| **Агент/Поведение** | Модель процесса | Агент — это процесс; поведение – это `main()` |
| **Когнитивные уровни** | Иерархия кольца привилегий | Уровень 1 (символический) → Уровень 5 (распределенный); ограниченный управлением |
| **ДПЭ** | Планировщик | Детерминированный граф задач; атомарность фиксации эпохи |

```text

│  Interfaces                                                 │
│  t81 studio (Human TUI)   t81 agent (AI-Native TUI)  CLI    │
├─────────────────────────────────────────────────────────────┤
│  T81Lang  — system language                                 │
```

**TISC ISA** — Замороженный набор команд. Каждое программное обеспечение компилируется под него. Семантика опкода и форматы проводов являются неизменяемыми в версии 1.x; расхождение является критическим дефектом.

**T81VM** — Механизм выполнения. Axion перехватывает огонь на границе отправки кода операции — до возникновения побочных эффектов — сохраняя путь управления вне цикла горячего интерпретатора.

**Axion** — Ядро. Перехватывает `AgentInvoke`, `AXREAD`, `AXSET`, `AXVERIFY`, коды операций вывода и вызовы FFI до возникновения побочных эффектов. Закрытие при сбое анализа политики; каждое мероприятие, посвященное CanonFS. По умолчанию агент не обладает никакими возможностями — каждое действие требует явного разрешения политики.

**CanonFS** — Файловая система. Веса моделей, объекты кода и артефакты времени выполнения хранятся в виде неизменяемых больших двоичных объектов, идентифицируемых хешем. Ядро Axion проверяет, соответствуют ли веса, загружаемые моделью, хешу в управляющей политике, устраняя атаки с подменой модели на уровне ОС.

**T81Lang** — язык системного программирования. Собственные типы: `BigInt`, `Fraction`, `Float`, `Complex`, `Tensor`, `Map`, `Set`, `Option`, `Result`. Объявления `agent`/`behavior` представляют собой модель процесса: агент — это первоклассный процесс; поведение является его точкой входа. В TISC они опускаются до `AgentInvoke`. `foreign {}` блокируется ниже `FFICall` (RFC-00B8).

**DPE** — Планировщик. Задачи объявляют неизменяемые входные данные; виртуальная машина фиксирует все записи атомарно в конце эпохи. Детерминированный параллелизм с замороженной ISA — новые коды операций не требуются.

## Как выглядит T81Lang

T81Lang — это язык системного программирования T81. Он компилируется в байт-код TISC и придает объявлениям `agent`/`behavior` первоклассный статус — агент является процессом; поведение является его точкой входа.

**Основные типы и арифметика:**

```t81
fn main() -> i32 {
  let greeting: T81String = "Hello, T81!";
  let ratio:    T81Float  = 3.14159t81;
  let big:      T81BigInt = 123456789t81;
  print(greeting);
  print(ratio);
  print(big);
  return 0;
}
```

**Агент/Поведение — модель процесса:**

```t81
// Агент — это именованный процесс. Его поведение является его точкой входа.
// Политика ядра Axion контролирует каждый вызов AgentInvoke перед выполнением.
Калькулятор агента {
  поведение add(a: i32, b: i32) -> i32 {
    вернуть а + б;
  }
}

fn main() -> i32 {
  пусть результат: i32 = Calculator.add(38, 4);
  печать (результат);   // 42
  вернуть 0;
}
```

**Запуск и компиляция:**

```sh
t81 code run program.t81                          # compile and execute
t81 code build program.t81 -o program.tisc        # compile to bytecode
t81 vm run program.tisc                           # execute bytecode directly
```

**С политикой Axion и моделью весов:**

```sh
t81 code run inference.t81 \
  --policy        secure_model.apl \
  --weights-model model.t81w \
  --trace
```

> **[Запустить игровую площадку T81Lang →](https://t81dev.github.io/t81-foundation/playground)**
>
> Пишите и запускайте программы T81Lang прямо в браузере. Полный компилятор + интерпретатор T81VM работает как WebAssembly. Восемь встроенных примеров: Hello World, арифметика BigInt, тензоры, агент/поведение и многое другое.

## Получите T81

### macOS / Linux

```sh
curl -fsSL https://github.com/t81dev/t81-foundation/releases/latest/download/install.sh | sh
```

Определяет архитектуру ОС и ЦП, загружает нужный двоичный файл, устанавливает на `~/.local/bin`. Установите `T81_INSTALL_DIR` для переопределения.

### Windows (PowerShell)

```powershell
irm https://github.com/t81dev/t81-foundation/releases/latest/download/install.ps1 | iex
```

Устанавливается на `%LOCALAPPDATA%\t81\bin`.

### Docker — 60 секунд, нулевой набор инструментов

```sh
docker run --rm -it ghcr.io/t81dev/t81-foundation demo
```

Извлекает образ размером около 100 МБ, запускает три программы (Hello World → троичные типы → проверка детерминированности), затем переходит в интерактивный REPL. Ни компилятора, ни CMake, ни настройки.

```sh
docker run --rm -it ghcr.io/t81dev/t81-foundation          # REPL only
docker run --rm -it ghcr.io/t81dev/t81-foundation <cmd>    # any t81 subcommand
```

### Питон (пип)

```sh
pip install t81
```

Устанавливает пакет Python `t81` для CPython 3.9–3.13 в Linux (x86\_64, ARM64), macOS (Apple Silicon, Intel) и Windows. Предоставляет `T81Int`, `BigInt`, `Float`, `Fraction`, `Tensor`, `HanoiVM`, `CanonFS` и полный API `compile`/`compile_and_run`. Колеса публикуются в PyPI в каждом выпуске с помощью рабочего процесса [`python-wheels`](.github/workflows/python-wheels.yml).

```python
import t81
result = t81.compile_and_run("fn main() -> i32 { return 42; }")
```

| **Собственная голая металлическая мишень** | 🚧 Альфа | T81 в настоящее время работает как уровень гостевой ОС в Linux и macOS; исполнение «голого металла» находится в активной разработке |
| **Последовательность загрузки QEMU** | 🚧 Альфа | EFI → «голое железо» → отдельно стоящий мост C++ подтвержден; `t81>` оболочка работает по последовательному порту — [см. ход загрузки](#ход-загрузки) |

Классификация поверхностей соответствует RFC-0048. Управляемые не-DCP и экспериментальные поверхности не представлены как проверенные детерминированные компоненты.

## Ход загрузки

Живая запись текущей последовательности загрузки QEMU AArch64 (последовательный вывод):

  <br><small>Текущий ход загрузки: EFI → «голое железо» EL1 → механизм политик → CanonFS mount → интерактивный t81> Prompt</small>

<br><small>Интерактивный повтор: <a href="https://github.com/t81dev/t81-foundation/blob/main/drivers/qemu/t81-boot.cast">t81-boot.cast (asciinema)</a></small>

T81 загружается на QEMU AArch64 (EDK2/UEFI). В таблице ниже показано завершение чистой загрузки с видимым на последовательном выводе приглашением оболочки — необходимое условие для записи демо-версии загрузки в этом README.

| Этап | Что он охватывает | Сделанный |
| :--- | :--- | :--- |
| **1. Загрузка EFI/UEFI** | PE32+ EFI загружает двоичные файлы, `ExitBootServices` завершается, передача на ядро ​​без ОС | 95% |
| **2. Запись ядра + инициализация HAL** | PL011 UART подтвержден на EL1; Автономный мост C++ инициализируется перед оболочкой | 95% |
| **3. EFI ↔ мост ядра C++** | Отдельно стоящий C++ (`-ffreestanding -fno-exceptions`), скомпилированный в BOOTAA64.EFI; вызывает баннер + оболочку из настоящего QEMU | 90% |
| **4. CanonFS крепление** | Драйвер в памяти всегда доступен при загрузке; постоянный драйвер активируется через `T81_CANONFS_ROOT` | 80% |
| **5. Оболочка/интерактивная подсказка** | Оболочка `t81>` с строковой буферизацией в последовательном порту; Команды `help` / `version` / `status` / `policy` | 95% |
| **6. Цикл событий ядра** | Приоритетная отправка (ошибки → прерывания → пейджер → галочка планировщика), WFI в режиме ожидания | 100% |
| | **Общий** | **~93%** |

**Текущее состояние:** Двоичный файл BOOTAA64.EFI представляет собой трехэтапный образ. Фаза 1 (EFI) печатает баннер ConOut и вызывает `ExitBootServices`. Фаза 2 (голый металл C) подтверждает доступ к EL1 PL011 MMIO. На этапе 3 (отдельно стоящий мост C++) печатается баннер управления и запускается интерактивная оболочка `t81>` — все это скомпилировано в один двоичный файл PE32+ без размещенной среды выполнения C++. Ожидаемая последовательная последовательность запуска Linux QEMU:

```текст
Axion QEMU AArch64 EDK2 слайс6

[axion] запись ядра EL1 без ОС
[аксион] ExitBootServices завершен; передача ядру C++

T81 -- Тернарная ОС для искусственного интеллекта
  ==========================

[axion] механизм политики: готов
[axion] canonfs: смонтировано (в памяти)
[axion] поток ядра tid=1: работает

т81>
```

**Осталось выполнить чистую загрузку:** драйвер Virtio-blk MMIO для постоянного CanonFS на «голом железе» (так что `T81_CANONFS_ROOT` имеет реальное блочное устройство в QEMU) и подключение размещенного цикла событий `KernelRuntimeState` (планировщик, пейджер, прерывания GICv3) к отдельно стоящему мосту, чтобы `status` отображал текущие счетчики.

Загрузочные сценарии, образ диска и захваченные последовательные выходные данные находятся в [`drivers/qemu/`](drivers/qemu/):

- [`drivers/qemu/scripts/launch_production.sh`](drivers/qemu/scripts/launch_production.sh) — загрузить образ в QEMU
- [`drivers/qemu/sample-boot-log.txt`](drivers/qemu/sample-boot-log.txt) — подтвержденная серийная последовательность из недавнего запуска.
- [`drivers/qemu/docs/QEMU_TESTING_RESULTS.md`](drivers/qemu/docs/QEMU_TESTING_RESULTS.md) — отчет о полной загрузке

Рабочий процесс CI [`qemu-boot`](.github/workflows/qemu-boot.yml) создает двоичный файл EFI, собирает образ FAT32 GPT, загружает его под QEMU (TCG cortex-a57 + EDK2 AArch64) при каждом нажатии, касающемся `userland/experimental/` или `drivers/qemu/`, проверяет все восемь маркеров загрузки на всех трех этапах и фиксирует обновленный последовательный журнал обратно в `drivers/qemu/sample-boot-log.txt`.

## Управление

T81 Foundation работает по модели **Непрерывного управления (C2)**. Все вклады должны поддерживать:

- **детерминированная четность выполнения** — хэши трассировки совпадают на всех поддерживаемых платформах.
- **архитектурная согласованность** — изменения детерминированной поверхности требуют формального рассмотрения.
- **специальные полномочия** — `spec/` > `docs/architecture/` > `docs/`; замороженные поверхности требуют обновления основной версии

Детерминированный реестр поверхностей определен в `docs/governance/DETERMINISM_SURFACE_REGISTRY.md`. Классификация границ поверхности (DCP/не-DCP, экспериментальная/выходящая за рамки области применения) определена в RFC-0048.

## Тройное преимущество

Хотя современное двоичное оборудование высоко оптимизировано для вычислений общего назначения, **сбалансированная троичная** ({-1, 0, +1}) имеет структурные свойства, которые особенно важны при детерминированном выполнении, управляемом выводе ИИ и нейронных нагрузках низкой сложности.

### 1. O(1) отрицание — распространение нулевого переноса

Отрицание двоичного дополнения до двух представляет собой побитовое НЕ, за которым следует +1, что может вызвать длинные цепочки переноса. Сбалансированное троичное отрицание меняет +1 ↔ −1 и оставляет 0 неизменным — **нет переноса, постоянное время**.

Измерено: Отрицание PackedCell достигает **~49,9 G-операций/с** на новейшем оборудовании x86\_64, что **~10,9× быстрее**, чем оптимизированное 64-битное целочисленное отрицание (проверено на Linux x86\_64 и macOS ARM64).

### 2. Превосходная базовая экономика

Теоретико-информационное оптимальное основание системы счисления равно *e ≈ 2,718*. Троичная система (основание 3) ближе к двоичной системе (основание 2), обеспечивая **~1,585 бит информации на трит** (log₂3). Более высокая энтропия на цифру, более компактные симметричные диапазоны — особенно полезно для весов, вложений и разреженных тензоров.

### 3. Внутренний побитовый детерминизм

IEEE 754 страдает от режимов округления, зависящих от платформы, различий в ассоциативности и ненормальной обработки. Сбалансированная тройная система симметрична относительно нуля: округление — это усечение без смещения по направлению. Каждый путь выполнения создает **идентичные хэши трассировки CanonHash81** на поддерживаемых платформах.

### 4. Нейронный вывод без умножения

Троичные веса {−1, 0, +1} сводят скалярные произведения к условному сложению/вычитанию — единица умножения не требуется. В сочетании с шестью кодами операций вывода TISC:

- Снижение энергопотребления в 15–60 раз по сравнению с базовыми показателями FP16/FP32
- Увеличение пропускной способности в 4–90 раз при сопоставимой точности
- Соответствует исследованиям BitNet b1.58, xTern и троичных преобразователей 2024–2026 гг.

Формат T81 Ternary Weight (T81WTN) и `t81 weights import` делают этот стек готовым к производству уже сегодня.

### 5. Хуки управления на уровне тритов

Поскольку TISC ISA является троичным, ядро ​​Axion может перехватывать и проверять переходы состояний с **детализацией на уровне тритов**, прежде чем возникнут побочные эффекты. Это обеспечивает принудительное применение политик, детальные этические шлюзы и детерминированные контрольные журналы, которые существенно более проверяемы, чем двоичное выполнение «черного ящика».

T81 спроектирован как автономная операционная система с собственным ISA и ядром, но собственного троичного оборудования пока не существует. Текущая предварительная версия работает как гостевой уровень в Linux/macOS/Windows через двоичные файлы, Docker или QEMU.

Это временная поддержка — точно так же, как ранние версии Linux работали на симуляторах до появления реального оборудования. Голый металлический ботинок находится в Альфа-версии; цель состоит в том, чтобы в конечном итоге полностью избежать зависимости от операционной системы хоста.
