# Фонд T81 — Стек детерминированных троичных вычислений

![Release](https://img.shields.io/badge/release-v1.9.0--Stable-blue)
![Tests](https://img.shields.io/badge/tests-369%2F369_passing-brightgreen)
![ISA](https://img.shields.io/badge/ISA-v1.2.0_Frozen-blue)
![Execution](https://img.shields.io/badge/execution-deterministic-green)
![CI](https://img.shields.io/badge/cross--platform--determinism-verified-brightgreen)
![License](https://img.shields.io/badge/license-MIT-lightgrey)

Используя теоретическую эффективность вычислений по основанию e, **Фонд T81** представляет собой стек детерминированных вычислений, построенный на **сбалансированной троичной арифметике** ({-1, 0, +1}) с полной моделью управления цепочкой, охватывающей набор инструкций, виртуальную машину, языковой компилятор и среду вывода ИИ.

Стек обеспечивает:

- **точная битовая воспроизводимость** — каждый путь выполнения создает идентичный хеш трассировки на поддерживаемых платформах
- **управляемый вывод ИИ** — механизм политик Axion перехватывает и проверяет каждую привилегированную операцию до появления побочных эффектов
- **происхождение, адресованное по контенту** — CanonFS неизменно записывает все артефакты, веса модели и состояние во время выполнения
- **детерминированное параллельное выполнение** — модель графа задач DPE (RFC-DPE-0002) позволяет выполнять параллельные рабочие нагрузки TISC с результатами, фиксируемыми по эпохам

### Ключевые компоненты

**TISC ISA v1.2** — Архитектура набора троичных инструкций. Заморожен в версии v1.x; неизменный контракт на выполнение для всего стека. В версии 1.2 добавлено 9 опкодов: `AgentInvoke` (RFC-0015), шесть операций троичного встроенного вывода (RFC-0034) и три управляемых операции FFI (RFC-00B8).

**T81VM** — Детерминированный интерпретатор TISC. Гарантирует побитово идентичный вывод на всех платформах; предварительная диспетчерская изоляция Axion держит хуки управления вне горячего пути выполнения. Полная диспетчеризация TISC v1.2, включая троичный встроенный вывод и FFI.

**Axion Governance Kernel** — Механизм политик, который перехватывает `AXREAD`, `AXSET`, `AXVERIFY`, опкоды ИИ и вызовы FFI перед любым побочным эффектом. Отказ при сбое анализа политики. Сертифицирован как Stable 2026-03-15 с 54/54 пройденными тестами.

**CanonFS** — Файловая система с адресацией по содержимому. Сохраняет все объекты кода, веса моделей и артефакты во время выполнения как неизменяемые BLOB-объекты, идентифицируемые по хешу. Обеспечивает происхождение для аудитов детерминизма.

**T81Lang** — Язык высокого уровня, нацеленный на байт-код TISC. Собственные типы: `BigInt`, `Fraction`, `Float`, `Complex`, `Tensor`, `Map`, `Set`. Первоклассные объявления `agent { behavior }` компилируются в `AGENT_INVOKE` с аудитом Axion (RFC-0015). Блоки `foreign [policy] { fn … }` объявляют управляемые внешние функции, которые вызываются через `FFI_CALL` (RFC-0036). `agent`, `behavior` и `foreign` можно использовать как контекстные идентификаторы во всех выражениях и позициях привязки. Конвейер компилятора: лексер → парсер → типизированное AST → семантический анализ → генерация IR.

**Ternary-Native Inference (RFC-0034)** — Шесть опкодов TISC для вывода ИИ без умножения с использованием сбалансированных троичных весов {−1, 0, +1}: `TWMATMUL` (матричное умножение), `TQUANT` (квантование до трита), `TATTN` (троичное внимание), `TWEMBED` (внедрение весов), `TERNACCUM` (скалярное произведение), `TACT` (активация с верхним вентилем Axion). Формат веса T81WTN. Фронтенд T81Lang `foreign {}` завершен через RFC-0036.

**Governed FFI (RFC-00B8 + RFC-0036)** — Полнофункциональный управляемый интерфейс внешних функций. Уровень VM (RFC-00B8 Phase 1): `FFIDispatcher` применяет проверки политик, квоты ресурсов и контрольные журналы перед любым внешним вызовом; `FFILibraryRegistry` отслеживает зарегистрированные библиотеки по имени и хешу версии; три опкода VM (`FFICall`, `FFIRegister`, `FFIPolicySet`). Уровень языка (RFC-0036): `foreign deterministic { fn sin(x: T81Float) -> T81Float; }` объявляет подписи; `foreign.sin(angle)` в местах вызовов снижается до `FFI_CALL` с именем функции, переданным в `text_literal`. Пройдено девять приемочных тестов.

**TUI Frontends** — Два дополнительных терминальных интерфейса, созданных на FTXUI v5.0.0:

- `t81 studio` — боковая панель навигации, обозреватель CanonFS, панель мониторинга Axion, визуализатор трассировки детерминизма, палитра команд (`Ctrl+P`)
- `t81 agent` — постоянная сессия JSONL, команды со слешем (`/compile`, `/run`, `/hash`, `/allow`, `/infer`, `/trits`, …), панель вероятности трита

**DPE (Deterministic Parallel Execution)** — Модель графа задач поверх замороженной ISA TISC. Задачи объявляют неизменяемые входы и буферизованные области вывода; VM фиксирует все записи атомарно в конце эпохи. Новых опкодов не требуется.

## Быстрый Старт

```bash
# Clone and configure
git clone https://github.com/t81dev/t81-foundation.git
cd t81-foundation
cmake --preset default -DCMAKE_BUILD_TYPE=Release
cmake --build build

# Run the full test suite
ctest --test-dir build --output-on-failure

# Launch the human operator TUI
./build/t81 studio

# Launch the AI-native TUI
./build/t81 agent

# Compile a T81Lang program
./build/t81 code build examples/hello.t81 -o hello.tisc

# Execute with Axion governance
./build/t81 vm run hello.tisc
```

Необязательные флаги сборки:

| Флаг | По Умолчанию | Назначение |
| :--- | :--- | :--- |
| `T81_BUILD_TUI` | `ON` | Фронтенды TUI на базе FTXUI |
| `T81_BUILD_TESTS` | `ON` | Полный набор тестов |
| `T81_ENABLE_ASAN` | `OFF` | Санитайзер адресов |
| `T81_ENABLE_UBSAN` | `OFF` | Санитайзер неопределенного поведения |
| `T81_ENABLE_LLAMA_CPP` | `OFF` | Управляемый адаптер вывода llama.cpp |
| `T81_WARN_STRICT` | `OFF` | Режим строгого сканирования предупреждений (используется предустановкой `warn-strict`) |

**Сканирование предупреждений перед отправкой (push)** — отображает проверки `-Wswitch`, `-Wunused-variable` и `-Wunused-function`, применяемые Windows CI, находя проблемы локально примерно за 2 минуты, вместо того чтобы ждать полную матрицу:

```bash
cmake --preset warn-strict
cmake --build build-warn-strict 2>&1 | head -40
```

## Управление

Фонд T81 работает в рамках модели **Непрерывного Управления (C2)**. Все вклады должны сохранять:

- **детерминированный паритет выполнения** — хеши трассировки должны совпадать на поддерживаемых платформах
- **архитектурную согласованность** — изменения, затрагивающие детерминированную поверхность, требуют формальной проверки
- **гарантии воспроизводимости** — никакого недетерминизма с плавающей запятой или недетерминизма, зависящего от платформы, в поверхности DCP

Детерминированная поверхность определена в `docs/governance/DETERMINISM_SURFACE_REGISTRY.md`. Изменения в замороженных поверхностях (TISC ISA, Data Types) требуют повышения основной (major) версии.

> **Заметка о границах:** Экспериментальные поверхности (Cognitive Tiers, Distributed, Trace-JIT, TernaryOS, адаптер llama.cpp) регулируются не-DCP и не должны представляться как проверенные детерминированные компоненты.

## Троичное Преимущество

Хотя современное бинарное оборудование оптимизировано в высокой степени, **Фонд T81** использует уникальные математические свойства **Сбалансированной Троичной Системы ({-1, 0, +1})** для достижения структурной эффективности, с которой не может сравниться бинарная система.

### 1. Вычислительная Симметрия $O(1)$

В двоичном дополнительном коде отрицание числа — это асимметричная операция (NOT + 1), которая требует распространения переноса. В T81 отрицание — это простое переключение трита (trit-flip) с **нулевыми накладными расходами на перенос**.

* **Производительность:** Пропускная способность отрицания в T81 достигает **~46.6 G-ops/s** (через `PackedCell`), превосходя оптимизированное 64-битное бинарное отрицание в **10.4x**.

### 2. Превосходная Экономия Основания

Основываясь на теореме о том, что наиболее эффективным основанием для системы счисления является $e \approx 2.718$, троичная система (Основание 3) математически более эффективна, чем бинарная (Основание 2).

* **Плотность Информации:** T81 достигает теоретической плотности **1.58 бита на трит**. Это преобразуется в более высокую энтропию за такт и уменьшенный объем занимаемой памяти для крупномасштабных систем координат и весов нейронов.

### 3. Битово-Точный Детерминизм

Бинарные операции с плавающей запятой (IEEE 754) часто страдают от недетерминированного округления, зависящего от платформы. Сбалансированная арифметика T81 обеспечивает:

* **Врожденную Симметрию:** Округление выполняется путем простого усечения, поскольку система естественным образом центрирована вокруг нуля.
* **Паритет Трассировки:** 100% "Точность Двунаправленного Прохода" на всех протестированных платформах (Linux x86_64, macOS ARM64) с нулевым расхождением в хешах трассировок VM.

### 4. Direct Governance Hook

Поскольку TISC ISA является троичной по своей природе, **Axion Governance Kernel** может проверять переходы состояний с более высокой детализацией. Операции вывода ИИ можно перехватывать на «уровне трита» (trit-level) до возникновения любых побочных эффектов, что обеспечивает модель безопасности с закрытием при отказе (fail-closed), которая архитектурно невозможна при стандартном бинарном выполнении «черного ящика».

# T81: Полный Отчет по Системам и Подсистемам

## 1. Краткий Обзор

T81 Foundation — это не одна программа. Это многоуровневый репозиторий, который объединяет троичную модель данных, ISA, VM, языковую/компиляторную поверхность, уровень управления, хранилище с адресацией по содержимому, механизмы бенчмарков и CI, экспериментальную разработку ОС/ядра, а также обширный аппарат управления/документации. Только корневой каталог репозитория показывает широкий охват системы: `.github`, `benchmarks`, `book`, `contracts`, `core`, `docs`, `experimental`, `kernel`, `lang`, `runtime`, `spec`, `src`, `tests`, `tooling`, `tools`, а также `internal`, `legacy`, `notebooks`, `pdf` и многоязычные/общедоступные ресурсы. Проект насчитывает 3636 коммитов и написан в основном на C++ с небольшими компонентами на Python/CMake/Shell/C. ([GitHub][1])

Самое сильное техническое ядро — это стек выполнения, ориентированный на детерминизм: типы данных, TISC, путь интерпретатора T81VM без JIT и связанный с ними реестр детерминизма / граница DCP. Эти области явно названы «Детерминированный Базовый Профиль» (Deterministic Core Profile), привязаны к артефактам проверки и подкреплены проверками CI и конкретными путями тестирования. Обзор архитектуры также четко отделяет замороженное/стабильное ядро ​​от экспериментальной периферии. ([GitHub][2])

Самая большая структурная слабость — это несогласованность статусов по всем поверхностям авторитета. Репозиторий представляет несколько конфликтующих версий зрелости/версий одновременно: в корневом README сказано «v1.9.0-Stable; 369/369 tests», в Центре Управления Проектом говорится «v1.4.1-Stable; 363/363 tests», `CMakeLists.txt` указывает версию `1.3.6`, спецификация TISC — «Version 1.1 — Stable», хотя в README описывается «TISC ISA v1.2», а ядро ​​Axion указано и как «Stable» в матрице внедрения, и как «Alpha» в нормативной спецификации и журнале прогресса экспериментальной ОС. Это не отменяет факта внедрения, но существенно снижает возможность аудита и внешний авторитет. ([GitHub][1])


## 2. Метод Оценки

Эта оценка основана на шести источниках доказательств: структура и история корня репозитория; нормативные спецификации в `spec/`; документы по архитектуре/управлению/статусу в `docs/`; поверхности сборки и CI, такие как `CMakeLists.txt` и `.github/workflows/ci.yml`; панели зрелости (maturity dashboards), такие как `PROJECT_CONTROL_CENTER.md` и `IMPLEMENTATION_MATRIX.md`; и журнал экспериментального прогресса ОС по пути `experimental/ternaryos/docs/PROGRESS.md`. Порядок авторитетности самого репозитория ясен: `/spec` > `docs/architecture/OVERVIEW.md` > `/docs` > `/book`. ([GitHub][1])

Таким образом, это аудит структуры/спецификации/поверхности реализации, а не полная построчная проверка исходного кода каждого файла C++. Если сам репозиторий заявляет статус реализации, тестов или зрелости, я рассматриваю это как утверждения, пока они не подкреплены смежными доказательствами, такими как проверки CI, явные пути тестирования или согласованность между документами. Если сам репозиторий содержит противоречия, я рассматриваю это как свидетельство отклонения в управлении. ([GitHub][3])

## 3. Карта Системы-Систем

### Архитектурные основы

Цель: определить ограниченную архитектуру, модель авторитета и границу детерминированного ядра. Основные расположения: `docs/architecture/OVERVIEW.md`, `docs/product/DETERMINISTIC_CORE_PROFILE.md`, `docs/governance/DETERMINISM_SURFACE_REGISTRY.md`, `spec/`. Зрелость: относительно высокая как поверхность управления документацией. Связанность: все зависит от этого. Ключевой риск: смещение статуса между этими файлами и публичными сообщениями верхнего уровня. ([GitHub][2])

### Модель данных / числовая модель

Цель: канонические троичные собственные типы данных и детерминированное кодирование. Основные расположения: `core/types/`, `spec/t81-data-types.md`, связанные тесты, перечисленные в DCP/реестре. Зрелость: среди наиболее заслуживающих доверия доменов; рассматривается как Замороженный/Проверенный (Frozen/Verified) в матрице реализации и DCP. Ключевой риск: область действия с плавающей запятой тщательно ограничена, но публичные сообщения могут размывать эти ограничения. ([GitHub][4])

### ISA / VM / среда выполнения (runtime)

Цель: замороженная семантика инструкций и детерминированная среда выполнения. Основные расположения: `core/isa/`, `core/vm/`, `runtime/`, `spec/tisc-spec.md`, `spec/t81vm-spec.md`. Зрелость: путь интерпретатора является основным рабочим субстратом; спецификация VM остается Beta, даже когда информационные панели переводят ее в статус Stable. Ключевой риск: рассогласование спецификаций/панелей и незаконченная эквивалентность JIT. ([GitHub][2])

### Язык / поверхности компилятора

Цель: детерминированный язык высокого уровня, компилируемый исключительно в TISC. Основные расположения: `lang/`, `spec/t81lang-spec.md`, фикстуры и шлюзы воспроизведения, названные в документах. Зрелость: сильнее, чем во многих экспериментальных языковых репозиториях, потому что он имеет нормативную грамматику, описание конвейера компилятора и явные оговорки о детерминизме. Ключевой риск: заявления о зрелости языка сильнее, чем непосредственно проверенные доказательства реализации здесь. ([GitHub][5])

### Управление / политика / Axion

Цель: контроль привилегированных инструкций, вердикты политики и прозрачность выполнения. Основные расположения: `kernel/axion/`, `spec/axion-kernel.md`, документы по управлению, документы, связанные с трассировкой. Зрелость: смешанная. Архитектура достаточно реальна, чтобы формировать дискурс VM и политики, но несколько основных заявлений об управлении в спецификации явно являются лишь частичными. Ключевой риск: риторика управления превосходит текущее исполнение в некоторых областях. ([GitHub][6])

### Хранилище / CanonFS / объектная модель

Цель: адресация по содержимому для обеспечения неизменности (persistence) и проверки происхождения (provenance). Основные расположения: `src/canonfs/`, `include/t81/canonfs/`, дополнительные спецификации и примечания к прогрессу ОС Axion. Зрелость: стабильность в пределах, указанных в документах по архитектуре; более амбициозные сценарии гостевой системы/загрузки/персистентности остаются экспериментальными на пути ОС. Ключевой риск: заявления о происхождении стабильного базового хранилища смешиваются с более широкими заявлениями о хранилище/загрузке прототипа. ([GitHub][2])

### Ядро / ОС / поверхности ОС Axion

Цель: субстрат операционной системы, MMU, планировщик, IPC, швы устройств/HAL, среда выполнения сервисов, каналы загрузки. Основные расположения: `experimental/ternaryos/`, `kernel/`, документы по прогрессу ОС. Зрелость: продвинутый размещенный (hosted) прототип, но еще не готовая операционная система. Ключевой риск: путаница в названиях между Axion как ядром управления и Axion как операционной системой. ([GitHub][7])

### ИИ / познание / поверхности вывода

Цель: троичный собственный вывод, когнитивные уровни (cognitive tiers), управляемые поверхности агента/среды выполнения, FFI, некоторые границы экспериментов с ИИ. Основные расположения: `experiments/ ai`, `experimental/`, функции, на которые ссылаются RFC в README/спецификациях. Зрелость: смешанная; работа над опкодом вывода кажется материально реализованной, в то время как когнитивный уровень и более широкие амбиции AGI/управления остаются отчасти спекулятивными или явно не входящими в DCP. Ключевой риск: чрезмерное расширение (overextension). ([GitHub][1])

### Тестирование / бенчмарки / обеспечение CI

Цель: обеспечение структурной целостности, утверждений о детерминизме, согласованности спецификаций/документации и бенчмарк-шлюзов. Основные расположения: `.github/workflows`, `benchmarks/`, `tests/`, `scripts/ci/`, `scripts/governance/`. Зрелость: сильная для стадии проекта. Ключевой риск: охват CI значителен, но некоторые задания носят информационный характер, а публичные цифры непоследовательны в разных документах. ([GitHub][1])

### Документация / публичная коммуникация

Цель: спецификации, аудиты, панели (dashboards), книга (book), многоязычные поверхности README. Основные расположения: `docs/`, `book/`, переводы README. Зрелость: очень высокая по количеству, смешанная по целостности синхронизации. Ключевой риск: разрастание документации (documentation sprawl) и конкурирующие уровни полномочий. ([GitHub][1])

### Устаревшее (Legacy) / внутреннее / ноутбуки / pdf / архив

Цель: история, вспомогательные артефакты, исследовательские материалы, сгенерированные материалы. Основные расположения: `legacy`, `internal`, `notebooks`, `pdf`, `artifacts/archive`. Зрелость: неясна по замыслу. Ключевой риск: мертвые поверхности, неясный статус поддержки, путаница среди участников. ([GitHub][1])

## 4. Подробная Инвентаризация Подсистем

### Типы Данных T81

Цель: каноническая числовая семантика и семантика коллекций. Расположения: `core/types/`, `spec/t81-data-types.md`, тесты, названные в DCP/реестре. Статус: реализовано, проверено и рассматривается как замороженное. Доказательства проверки: `v1_canonical_numeric_contract_test.cpp`, `tisc_binary_io_determinism_test.cpp`, плюс примечания к аудиту в матрице реализации. Отношение к детерминизму: основополагающее. Отношение к управлению: высокое, потому что канонизация и воспроизведение политик зависят от стабильных представлений. Основное опасение: сообщения о плавающей запятой должны оставаться ограниченными (bounded). ([GitHub][4])

### TISC ISA

Цель: неизменный контракт выполнения. Расположения: `core/isa/`, декодирование/диспетчеризация VM, `spec/tisc-spec.md`. Статус: операционное ядро, но отчеты о статусе/версии противоречивы: матрица реализации рассматривает его как замороженное/проверенное, README говорит о v1.2, в то время как страница спецификации — «Версия 1.1 — Stable», а CI по-прежнему ссылается на «Verify TISC v1.1.0 Freeze Integrity». Отношение к детерминизму: максимальное. Отношение к управлению: видимость Axion нормативна в спецификации. Основное опасение: целостность замораживания строго управляется, но учет версий представлен непоследовательно. ([GitHub][4])

### Интерпретатор T81VM

Цель: детерминированная среда выполнения для TISC. Расположения: `core/vm/`, `spec/t81vm-spec.md`. Статус: практически центральный и рассматривается информационными панелями как стабильный (stable), но все еще Beta в нормативной спецификации. Доказательства проверки: тесты трассировки VM и свойств детерминизма, включение в DCP, упоминания о соответствии. Отношение к детерминизму: максимальное. Отношение к управлению: явная интеграция с Axion. Основные опасения: публичный `get_execution_mode()` не раскрыт (not exposed); события планирования (scheduling events) еще не являются записями трассировки первого класса; гарантии кросс-архитектурности для вычислений с плавающей запятой явно ограничены. ([GitHub][8])

### T81Lang

Цель: детерминированный язык высокого уровня, ориентированный на TISC. Расположения: `lang/`, `spec/t81lang-spec.md`, фикстуры/скрипты воспроизведения (repro), названные в реестре. Статус: одна из наиболее сильных подсистем по документации и заявленному состоянию продвижения. Доказательства проверки: детерминированные фикстуры, шлюзы воспроизведения (repro gates), полная грамматика, описание конвейера. Отношение к детерминизму: высокое, но с явными оговорками относительно трансцендентного/плавающего поведения, зависящего от хоста. Отношение к управлению: осведомленность об уровнях (tier-awareness), чистота/эффекты, видимость Axion. Основные опасения: заявления о зрелости превышают то, что можно независимо подтвердить на основе непосредственно проверенных здесь поверхностей реализации. ([GitHub][5])

### Axion Governance Kernel

Цель: слой политики и контроля над выполнением. Расположения: `kernel/axion/`, `spec/axion-kernel.md`. Статус: частично реальный и частично устремленный в будущее (aspirational). Матрица реализации повышает его до Stable с 54/54 тестами, но нормативная спецификация все еще говорит Alpha и явно признает частичную реализацию управления детерминизмом и неполные метрики сложности. Отношение к детерминизму: высокое. Отношение к управлению: это ядро управления. Основное опасение: архитектура значительна, но язык «последнего арбитра» опережает реализованные возможности обнаружения. ([GitHub][4])

### CanonFS

Цель: неизменное происхождение и хранение, адресуемое по содержимому (content-addressed provenance and persistence). Расположения: `src/canonfs/`, `include/t81/canonfs/`, дополнительная документация/спецификации. Статус: ограниченно-стабильный (stable-bounded) в обзоре архитектуры и документах, связанных с DCP; более продвинутые заявления о персистентности и начальной загрузке гостевой системы (guest-bootstrap) относятся к пути экспериментальной ОС. Доказательства проверки: указанные пути исходного кода и тесты фазы ОС. Основное опасение: репозиторий смешивает заявления о стабильном базовом происхождении с более широкими работами по долговечности гостевой системы/загрузки, которые все еще явно находятся на стадии прототипа. ([GitHub][2])

### Профиль Детерминированного Ядра (DCP) / Реестр

Цель: определить границу сертификации и проверенные детерминированные поверхности. Расположения: `docs/product/DETERMINISTIC_CORE_PROFILE.md`, `docs/governance/DETERMINISM_SURFACE_REGISTRY.md`. Статус: реальный механизм управления, а не просто брендинг. Доказательства проверки: явное сопоставление поверхность/тест/CI. Основное опасение: граница DCP — это хорошая инженерия, но более широкий нарратив репозитория иногда размывает ее. ([GitHub][9])

### Скрипты CI / Управления (Governance)

Цель: обеспечение структуры, согласованности документов/спецификаций, целостности замораживания, гигиены рабочих процессов (workflow hygiene), проверок управления, выравнивания DCP и шлюзов бенчмарков. Расположения: `.github/workflows/ci.yml`, `scripts/ci/`, `scripts/governance/`. Статус: необычно сильный для репозитория экспериментальных систем. Основное опасение: широта впечатляет, но информационные задания не приравниваются к доказательствам готовности к производству (production evidence), и проинспектированный файл CI сам по себе является лишь одной частью инфраструктуры рабочих процессов. ([GitHub][3])

### Бенчмарки (Benchmarks)

Цель: проверка производительности и рабочих нагрузок (performance and workload gates). Расположения: `benchmarks/`, шлюз бенчмарков в CI, заявления о бенчмарках в README. Статус: присутствует и работает достаточно для того, чтобы блокировать некоторые работы (gate some work), но дисциплина бенчмарков еще не полностью унифицирована с отчетами о стабильных релизах. Основное опасение: заявления о производительности в маркетинговых разделах README более обширны, чем веские доказательства, проинспектированные здесь. ([GitHub][1])

### ОС Axion / TernaryOS

Цель: размещенный (hosted) субстрат ядра/ОС с MMU, планировщиком, IPC, устройствами, пейджером, средой выполнения сервисов, загрузочными каналами. Расположения: `experimental/ternaryos/`, `kernel/`, журнал прогресса ОС. Статус: продвинутый размещенный прототип с существенными доказательствами пошаговой (slice-by-slice) реализации. Основное опасение: несмотря на реальную инженерную глубину, он остается явно экспериментальным, размещенным и частично построенным на рабочих процессах QEMU/VirtualBox/dev-lane, а не зрелой автономной ОС. ([GitHub][7])

### TUI / CLI / Инструментарий

Цель: фронтенды оператора и агента, рабочие процессы разработчика, примеры. Расположения: `tools/`, `tooling/`, `examples/`, опция `T81_BUILD_TUI`, документация README. Статус: реализован достаточно, чтобы поставляться и описываться, но не является центральным для доверия к системе. Основное опасение: широта UI/инструментария может опережать стабилизацию основных архитектурных границ. ([GitHub][10])

### Экспериментальное / Распределенное / Когнитивные Уровни / ИИ

Цель: пути расширения вне DCP (non-DCP). Расположения: `experimental/`, `experiments/ ai`, `runtime/jit/`, ссылки на распределенные и уровневые системы в DCP/реестре. Статус: на стадии исследований или заглушки (stubbed), согласно собственным определениям репозитория. Основное опасение: эти поверхности расширяют область действия (scope) быстрее, чем добавляют эксплуатационные доказательства (operational proof). ([GitHub][1])

## 5. Оценка Согласованности Архитектуры

Существует реальная многоуровневая модель. Обзор архитектуры представляет согласованную цепочку от T81Lang до TISC, T81VM, Axion и CanonFS, при этом экспериментальные уровни (tiers) явно показаны как необязательные/не-DCP. DCP и реестр детерминизма подкрепляют это, сужая гарантии до названных проверенных поверхностей. Это сильный признак архитектурного самосознания. ([GitHub][2])

Однако границы подсистем лишь частично реальны. Граница основного выполнения кажется достаточно реальной: типы данных, ISA, интерпретатор и выбранные детерминированные поверхности сериализации/тестирования. За пределами этого ядра границы размываются. «Axion» относится как к ядру управления в стабильном стеке, так и к экспериментальной операционной системе. Спецификация T81VM имеет статус Beta, в то время как панели управления (dashboards) называют ее Stable. Спецификация Axion имеет статус Alpha, в то время как матрица реализации называет Axion Kernel Stable. Документ о прогрессе ОС по-прежнему использует внутреннее имя `ternaryos`. Это не мелкая проблема формулировки; это означает, что архитектура имеет несколько перекрывающихся самоописаний. ([GitHub][6])

Интерфейсы частично явные, частично неявные. В спецификациях хорошо описаны требуемые поведения, инварианты и программы соответствия (conformance programs). CI также включает проверки согласования. Но несколько критических интерфейсов по-прежнему отслеживаются как неполные или косвенные: режим выполнения виртуальной машины не раскрыт через чистый публичный API; события планировщика не являются первоклассными (first-class) событиями трассировки; активное обнаружение недетерминизма в Axion реализовано лишь частично. Это означает, что некоторые контракты лучше специфицированы, чем реализованы. ([GitHub][8])

Самые сильные швы (seams) — это граница DCP и внутренняя модель авторитета (authority model) репозитория. Самые слабые швы — синхронизация имен/версий/статусов и расширение от строгого детерминированного ядра до ОС, познания (cognition), ИИ и нарративов аппаратного обеспечения. Разрастание документации видно по дереву репозитория и плотной экологии панелей управления. ([GitHub][1])

## 6. Оценка Детерминизма и Воспроизводимости

Детерминизм — самая серьезная инженерная тема в репозитории. О нем заявляется в README, он формализован в спецификациях TISC и T81VM, ограничен в обзоре архитектуры, сужен в DCP и перечислен в Реестре Поверхностей Детерминизма. Реестр особенно полезен, поскольку отличает проверенные поверхности от исключенных или запланированных. ([GitHub][1])

Где детерминизм действительно обеспечивается: семантика опкодов TISC, выполнение интерпретатора виртуальной машины, каноническое кодирование типов данных и детерминированная математика с программной плавающей запятой (soft-float) — все это указано как проверенное с названными тестами и принудительным выполнением в CI. Затем DCP использует этот реестр как шлюз (gate) для гарантий релиза. CI дополнительно запускает проверки целостности замораживания (freeze-integrity), проверки согласованности архитектуры и проверку заявлений о детерминизме. ([GitHub][11])

Где детерминизм только частичный или ограниченный: генерация байт-кода компилятором явно указана как «Частичная» в реестре; эквивалентность JIT запланирована, а не проверена; сетевой ввод-вывод, планирование в реальном времени, аппаратное поведение FPU вне программной плавающей запятой и детерминизм производительности явно выходят за рамки. В T81Lang также указано, что деление с плавающей запятой и трансцендентное поведение могут варьироваться в зависимости от архитектуры. Это хорошая инженерная честность. ([GitHub][11])

Основное несоответствие не в амбициозности технических задач по сравнению с нулевой реализацией; а в технических амбициях по сравнению с дисциплиной статусов. Репозиторий имеет хорошо продуманную границу детерминизма, но его публичные поверхности версий/статусов достаточно противоречивы (noisy), чтобы подорвать уверенность в точности релизов. В проекте, построенном вокруг побитово точной воспроизводимости (bit-exact reproducibility), точность версий также имеет значение. ([GitHub][9])

## 7. Управление, Безопасность и Оценка Уровня Политик

Управление (Governance) здесь носит архитектурный характер, а не является чисто риторическим. Axion присутствует в спецификациях ISA и VM, в обзоре архитектуры, в границах DCP и в матрице реализации. CI репозитория также содержит множество проверок управления и проверок на завышенные обещания (overclaim checks), что сильнее, чем традиционная модель управления, описанная только в README. ([GitHub][12])

С учетом сказанного, сама спецификация показывает, что уровень управления не полностью реализован. «Управление детерминизмом» (determinism stewardship) в Axion явно частичное; активное обнаружение недетерминизма еще не реализовано. Измерение сложности является частичным. Спецификация также отмечает, что конкатенация строк канонических причин была отслеживаемым пробелом (tracked gap). Таким образом, стек управления реален, но еще не достаточно полон, чтобы оправдать более широкое представление репозитория о «наблюдательном интеллекте» (supervisory intelligence) без оговорок. ([GitHub][6])

Наиболее убедительным механизмом управления является не «этический» язык; а ограниченный перехват привилегированных операций политиками плюс явные требования к отслеживаемости. Наименее убедительной частью является распространение языка управления на когнитивный уровень и надзор за продвинутыми рассуждениями (advanced reasoning supervision), в то время как основные механизмы обнаружения и метрик еще неполны. ([GitHub][6])

## 8. Проверка Реальности Реализации

Что действительно работает сейчас: профиль детерминированного ядра вокруг типов данных, TISC, путь интерпретатора T81VM, избранные фикстуры воспроизводимости компилятора, существенный стек CI/управления и достаточная интеграция Axion для закрепления заявлений о выполнении с учетом политик (policy-aware execution). Репозиторий имеет конкретные тесты, названные рабочие процессы и явные обозначения стабильности/замороженности (stable/frozen) вокруг этого ядра. ([GitHub][9])

Что работает частично: части более богатой модели управления Axion (stewardship model), некоторые поверхности компилятора и воспроизводимости, поверхности сервисов/запросов в работе над ОС, а также дисциплина бенчмарков/релизов как полностью синхронизированная поверхность управления. Они не отсутствуют; просто они не так полны, как предполагает наиболее амбициозный язык репозитория. ([GitHub][6])

Что кажется смонтированным (scaffolded), но еще не работающим в самом строгом смысле: эквивалентность trace-JIT, детерминизм распределенных/когнитивных уровней, внешние аппаратные ускорители, реальные аппаратные адаптеры в пути ОС и более широкие амбиции в отношении «глобальной детерминированной вычислительной платформы». Сам репозиторий классифицирует многие из них как экспериментальные, запланированные или выходящие за рамки DCP. ([GitHub][9])

Самые зрелые области: типы данных детерминированного ядра, ISA, интерпретатор, леса CI/управления (CI/governance scaffolding) и — судя по зрелости документации — поверхность языка. Наиболее устремленные (aspirational) области: полное управление интеллектом (full governance intelligence), распределенные/когнитивные уровни, реализация на нативном аппаратном обеспечении (native hardware realization) и превращение ОС в субстрат ядра общего назначения. ([GitHub][4])

## 9. Оценка Тестирования, Верификации и CI

Позиция тестирования/CI является основным преимуществом. Проверенный рабочий процесс CI включает в себя проверку структуры, проверки целевой архитектуры, проверки целостности замораживания TISC, проверки границ экспериментов ИИ, проверки согласованности архитектуры, закрепление рабочего процесса и аудит разрешений, большой набор проверок управления, проверки целостности DCP, метрики управления и шлюзы рабочих нагрузок (workload gates) бенчмарков. Это существенно более строго, чем в типичном любительском системном репозитории. ([GitHub][3])

Репозиторий также связывает заявления о детерминизме с указанными тестами и скриптами таким образом, что это удобно для аудита. Реестр детерминизма и DCP перечисляют явные пути, а не смутные заверения. Это правильный шаблон (pattern). ([GitHub][11])

Слепые пятна остаются. Некоторые задания CI являются информативными, а не жесткими шлюзами (hard gates). Генерация байт-кода компилятором является лишь частичной в реестре детерминизма. Сама спецификация виртуальной машины допускает отсутствие прямых поверхностей запросов и неполную видимость трассировки планирования. Показатели бенчмарков/отчетов противоречивы в разных авторитетных документах. ([GitHub][3])

## 10. Оценка Целостности Документации и Спецификаций

Количество документации очень велико, а намерение инженерного контроля серьезно. В обзоре архитектуры явно указан порядок подчиненности (authority ordering). Матрица внедрения пытается сократить расхождение в описаниях до одной строки на подсистему. Центр контроля проектов централизует статусы этапов (gate status). Это пример хорошего проектирования управления. ([GitHub][2])

Проблема кроется в целостности синхронизации. В изученных материалах видны как минимум пять основных несоответствий: версия README/количество тестов в сравнении с данными Центра Контроля Проекта и версией CMake; TISC v1.2 в сравнении со спецификацией TISC v1.1; бета-спецификация T81VM в сравнении со стабильной панелью управления (Stable dashboard); альфа-спецификация Axion в сравнении со стабильной матрицей внедрения (Stable matrix); и заявления о альфа-версии/прототипе ОС Axion в сравнении с более общими формулировками о стабильном ядре в других местах. Эти вещи не носят косметический характер. Они создают неопределенность относительно того, что следует считать авторитетным для нового разработчика, партнера или оценщика. ([GitHub][1])

Для нового технического участника репозиторий впечатляет, но его сложно анализировать. Наличие папок `docs`, `book`, `spec`, `contracts`, `internal`, `legacy`, `pdf`, `notebooks`, множества панелей управления и многоязычных публичных материалов дает понять, что это среда с большим объемом документации. Без строгой синхронизации она превращается в лабиринт. ([GitHub][1])

## 11. Оценка Ядра / ОС / Axion

Работа над ОС зашла гораздо дальше, чем просто концептуальная записка. В журнале прогресса описаны реализованные этапы для MMU, планировщика/IPC, хранения данных (persistence), заглушек (scaffolds) для устройств, ABI пейджера (pager), срезов управления прерываниями (interrupt governance slices) и проверки загрузочных каналов. В нем цитируются тысячи проверок (assertions) и поэтапный план развития с конкретными файлами и тестами. Это реальная инженерная работа. ([GitHub][7])

Однако его по-прежнему лучше всего классифицировать как продвинутый размещенный прототип (advanced hosted prototype), а не полноценное ядро. В журнале прогресса неоднократно описываются пути моделирования в хостовой системе, среды разработки (developer lanes) QEMU, заглушки VirtualBox, пакеты передачи восстановленных артефактов (recovered-artifact handoff bundles) и открытые работы над адаптерами реального оборудования. Архитектура развивается поэтапно (staged slices), а проверка опирается на симуляцию; это заслуживает уважения, но не равносильно зрелой независимой операционной системе. ([GitHub][7])

Разделение терминологии также имеет значение. «Axion» относится к операционной системе в журнале прогресса, в то время как спецификация определяет «Ядро Axion» (Axion Kernel) как уровень надзора и контроля (supervisory intelligence) экосистемы. Эти концепции связаны, но не идентичны. Это столкновение терминов (naming collision) будет продолжать вызывать путаницу, пока в репозитории не будет проведена более жесткая семантическая граница. ([GitHub][7])

Вердикт: на данный момент это продвинутый архитектурный прототип / частичный субстрат ОС с реальными подсистемами, но еще не готовая ОС общего назначения или производственная ОС. ([GitHub][7])

## 12. Оценка Стека Язык / VM / ISA

TISC — самый стабильный концептуальный якорь. Он является нормативным, ориентирован на фиксацию (frozen-oriented) и явно определяет детерминированное выполнение, нулевое неопределенное поведение, видимость Axion и совместимость с типами данных, VM и языковыми слоями. ([GitHub][12])

T81VM — это операционное ядро. Путь интерпретатора явно занимает центральное место в детерминированном ядре, и DCP исключает JIT до тех пор, пока не будет доказана его эквивалентность. Спецификация также демонстрирует здоровую честность, называя незавершенные в настоящее время области, а не делая вид, что они готовы. ([GitHub][8])

T81Lang более зрел, чем многие исследовательские языки, так как у него есть нормативная грамматика, типизация/эффекты, явные примечания о детерминизме и конвейер компиляции. Однако именно здесь амбиции проекта легче всего выходят за рамки возможного. Статус языка «Stable» является правдоподобным для ограниченной инструментальной цепочки от компилятора до TISC, но не обязательно для полной семантики экосистемы, подразумеваемой в отношении уровней (tiers), агентов (agents) и управляемых внешних поверхностей (governed foreign surfaces), без более жестких ограничений для релиза. ([GitHub][5])

В качестве стабильного субстрата вычислений, комбинация типы данных + TISC + не-JIT T81VM является наиболее надежным техническим активом репозитория. Именно эту часть можно правдоподобно рассматривать как серьезную экспериментальную платформу. ([GitHub][9])

## 13. Оценка Исследования vs Продуктивизация

На сегодняшний день репозиторий находится между «экспериментальной платформой» и «технической основой перед созданием продукта». Он выходит за рамки простого исследовательского артефакта, поскольку имеет системы сборки, CI, тесты, документы о дисциплине выпуска релизов, ссылки на соответствие стандартам (conformance references), панели управления и ограниченное детерминированное ядро. Тем не менее, он пока не является платформой для разработчиков или кандидатом в инфраструктурное решение в прямом смысле этого слова, так как слишком много внешних слоев по-прежнему остаются экспериментальными, противоречивыми или перегруженными управлением по сравнению со степенью их готовности. ([GitHub][3])

Чтобы перейти на следующий этап, репозиторию потребуется одно решающее изменение: отделение сертифицируемого детерминированного ядра от исследовательской (exploratory) экосистемы с помощью гораздо более жесткой маркировки релизов. Это означает единый авторитетный источник версий, единый источник статусов, единый реестр продвигаемых компонентов и четкие пометки «не является частью продукта» везде, где это применимо. После этого потребуется независимое воспроизведение результатов вне контекста основных разработчиков и более строгие доказательства надежности интерфейсов языка/цепочки инструментов/управления, которые он уже заявляет как стабильные. ([GitHub][9])

## 14. SWOT Анализ

**Сильные стороны (Strengths)**
Репозиторий имеет реальную системную архитектуру, а не только брендинг. Граница детерминизма проведена на удивление четко. Дисциплина CI/Управления (Governance) находится на высоком уровне. Вычислительное ядро, основанное на интерпретаторе (interpreter-centered execution core), выглядит вполне реальным. Проект также отличается сильными традициями в области документирования и нацеленностью на работу с различными уровнями (cross-layer intent). ([GitHub][2])

**Слабые стороны (Weaknesses)**
Несоответствие статусов/версий является серьезной проблемой. Документация чрезмерно разрослась (Documentation sprawl). Терминология управления (Governance language) иногда опережает реальную реализацию. ОС и продвинутые функции ИИ/управления расширяют масштаб быстрее, чем добавляют проверяемой надежности (auditable certainty). Пересечения в названиях (Naming collisions), особенно вокруг Axion, размывают архитектуру. ([GitHub][13])

**Возможности (Opportunities)**
Релиз четко ограниченного детерминированного ядра мог бы стать надежной отправной точкой проекта в сферу научных вычислений, воспроизводимого выполнения или экспериментов с языками/VM. В репозитории уже есть управленческая база для поддержки этого, если он перестанет пытаться представить каждый внешний уровень таким же зрелым, как и ядро. ([GitHub][9])

**Угрозы (Threats)**
Самая большая угроза — это потеря доверия из-за расхождения между заявлениями и реальностью (overclaim drift). В проекте, построенном вокруг детерминизма и проверяемости (auditability), противоречивые данные о статусе особенно разрушительны. Вторая угроза — коллапс сопровождаемости из-за чрезмерной широты охвата: ядро, язык, VM, хранилище, ИИ, аппаратное обеспечение, документы, книга, информационные панели и многоязычное информирование — и все это под единым, постоянно меняющимся графом полномочий (authority graph). ([GitHub][1])

## 17. Стратегические Рекомендации

### Ближайшие приоритеты (0–30 дней)

Унифицируйте авторитетный источник версий/статусов (version/status authority). Выберите один канонический источник для номера релиза, зрелости спецификаций, зрелости подсистем и общего количества тестов; генерируйте README, Центр Управления (Control Center), Матрицу Реализации (Implementation Matrix) и метаданные сборки на его основе. Пока это не будет сделано, каждое заявление о «стабильности» должно рассматриваться как предварительное. ([GitHub][1])

Переименуйте две концепции Axion. Одна — это ядро управления/механизм политик (governance kernel/policy engine); другая — экспериментальная операционная система. Им нужны разные пользовательские имена или строгие префиксы. ([GitHub][6])

Опубликуйте индекс статуса поддержки репозитория по каталогам верхнего уровня: поддерживаемое ядро (maintained core), поддерживаемая база (maintained support), экспериментальное (experimental), устаревшее (legacy), архив (archived), только внутреннее (internal-only). Дерево слишком большое, чтобы оставлять это неявным. ([GitHub][1])

### Краткосрочные приоритеты (1–3 месяца)

Ужесточите правила перевода из спецификации в реализацию (spec-to-implementation promotion rules). Подсистема не должна называться Stable на панелях управления, пока ее нормативная спецификация остается Beta/Alpha, за исключением случаев, когда в репозитории явно различаются «стабильная реализация, ожидающая спецификации» (implementation stable, spec pending). В настоящее время это делается не совсем чисто. ([GitHub][8])

Завершите недостающие поверхности наблюдаемости (observability surfaces) на границе VM/Axion: прямой запрос режима выполнения (direct execution-mode query), первоклассные события трассировки планирования (first-class scheduling trace events) и все, что осталось от работы по каноническим строкам причин (canonical reason-string) и обнаружению недетерминизма. Это точки приложения усилий (leverage points), поскольку они превращают управление из философии в инструментарий. ([GitHub][8])

Отделите примечания к выпуску (release notes) DCP от примечаний к выпуску экосистемы. Ядро заслуживает компактной (lean), сертифицируемой дисциплины релизов. Более широкая экосистема заслуживает журнала прогресса исследований. Их смешивание притупляет (blunts) и то, и другое. ([GitHub][9])

### Среднесрочные приоритеты (3–12 месяцев)

Добейтесь независимого внешнего воспроизведения (independent external reproduction) детерминированного ядра, поскольку сам репозиторий называет это оставшимся критерием продвижения для проверки в стиле Этапа 2. Это сделало бы для доверия больше, чем еще один слой информационных панелей. ([GitHub][1])

Для работы над ОС выберите следующее испытание на истинность: либо «размещенный прототип со строгой симуляцией устройств/загрузки» (hosted prototype with rigorous device/boot simulation), либо «субстрат реального ядра на ограниченной целевой платформе» (real kernel substrate on a constrained target). В настоящее время она ответственно прогрессирует, но все еще по слишком многим этапам (staged lanes). Более узкая цель приемки (acceptance target) сделала бы программу более четкой. ([GitHub][7])

Что касается периметра ИИ/управления, прекратите продвигать концепции когнитивных систем/распределенных систем/аппаратного обеспечения (cognitive/distributed/hardware visions) как почти равные ядру. Держите их в каналах исследований, явно не относящихся к DCP (explicitly non-DCP research channels), пока они не будут иметь такую же плотность доказательств, как стек VM/ISA/data-type. ([GitHub][9])

## 18. Окончательный Вердикт

На сегодняшний день T81 Foundation является, по большей части, **строгой экспериментальной платформой детерминированных вычислений с реальным ядром VM/ISA/data-model и необычно сложной надстройкой управления/документации (governance/documentation superstructure)**. ([GitHub][2])

Его самым сильным техническим активом является **ограниченный профиль детерминированного ядра (bounded deterministic core profile) и тот факт, что репозиторий фактически пытается связать заявления (claims) с названными тестами, проверками CI и явными исключениями из области действия**. ([GitHub][9])

Его самой большой структурной слабостью является **несогласованность статусов (status incoherence) в спецификациях, панелях управления (dashboards), README и метаданных сборки**. В обычном репозитории это раздражает. В репозитории, построенном на детерминизме и возможности аудита, это разрушительно (corrosive). ([GitHub][1])

Единственным шагом, который бы больше всего улучшил его траекторию, было бы **превращение самой синхронизации (synchronization itself) в первоклассную детерминированную поверхность**: один граф авторитета (authority graph), один сгенерированный реестр зрелости (maturity ledger), одна истина релиза (release truth) и жесткое разделение между сертифицируемым ядром (certifiable core) и исследовательской границей (exploratory frontier).
