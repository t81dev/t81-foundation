# Глава 2: Основные принципы и инварианты

## 2.1 Инвариант детерминизма

**Статус: Реализовано и протестировано**

Центральной аксиомой архитектуры T81 является **Строгий детерминизм**. В этой системе программа $P$ — это не рекомендация для оборудования; это математическое определение функции перехода состояний $f$.

Формально, задав начальное состояние $S$ и входной вектор $I$, функция должна удовлетворять условию:
$$
\forall \text{hardware } H: \text{Exec}_H(S, I) \to S' \implies S' \text{ is invariant}
$$

Достижение этого требует устранения всех источников недетерминизма, обычных для современных вычислений. T81 рассматривает хост-среду (ОС, ЦП, FPU) как "состязательный источник энтропии", который необходимо ограничивать.

### 2.1.1 Поверхности детерминизма и векторы атак

"Поверхность детерминизма" — это граница, где абстрактная машина взаимодействует с физической реальностью. Любая утечка физической реальности (время, случайный шум, аппаратные особенности) в логическое состояние представляет собой **Нарушение детерминизма**.

| Уровень  | Риск детерминизма            | Мера устранения           | Доказательство реализации |
| :--- | :--- | :--- | :--- |
| **Компилятор** | Порядок токенов, итерация map | Каноническая сортировка AST | `src/frontend/ast.cpp` (Отсортированные Map) |
| **VM** | Утечка адресов памяти        | Непрозрачные дескрипторы (Индексы) | `src/vm/vm.cpp` (Сегменты памяти) |
| **GC** | Недетерминированная сборка   | Триггеры по числу аллокаций | `src/vm/gc.cpp` (GC на основе инструкций) |
| **Параллелизм** | Гонки, планирование | Кооперативные корутины | `src/vm/scheduler.cpp` (Детерминированные тики) |
| **Float**    | Дрейф FPU хоста (IEEE-754)   | Программный float `dmath` | `include/t81/core/T81Float.hpp` |
| **Трансцендентные** | Вариативность реализации Libm | Ряды Тейлора (Фикс. итерации) | `include/t81/core/detail/dmath.hpp` |
| **JIT**      | Расхождение оптимизации      | Проверки эквивалентности трасс | `src/vm/jit_compiler.cpp` |

### 2.1.2 "Разрыв Libm" и `dmath`
Критической уязвимостью кросс-платформенного детерминизма является "Разрыв Libm" (Libm Gap). Стандарт IEEE-754 определяет форматы с плавающей запятой, но оставляет трансцендентные функции (sin, cos, pow) слабо специфицированными. В результате `std::sin(x)` на x86_64/GLIBC может отличаться на 1 ULP (единицу в последнем разряде) от `std::sin(x)` на ARM64/MUSL.

T81 решает эту проблему с помощью **`dmath`** (Детерминированная Математика), собственной библиотеки, которая реализует:
*   **Арифметика Soft-Float**: `Add`, `Sub`, `Mul` побитово точны.
*   **Собственные Трансцендентные**: `Sin`, `Cos`, `Exp` реализованы через ряды Тейлора/Маклорена с фиксированным числом итераций и фиксированными константами, игнорируя `libm` хоста.
*   **Режим округления**: Округление до четного (ties-to-even) принудительно задается программно.

> **Инвариант**: $\text{dmath::sin}(x)$ производит абсолютно идентичный битовый паттерн на Intel i9, Apple M3 и плате разработки RISC-V.

## 2.2 Троичная логика (Основание-3)

**Статус: Реализовано и протестировано**

T81 — это **сбалансированная троичная** система. Фундаментальной единицей является **трит** со значениями $\{-1, 0, 1\}$ (часто обозначается как $-, 0, +$ или $T, 0, 1$).

### 2.2.1 Почему троичная?
1.  **Симметричная арифметика**: Диапазон значений симметричен относительно нуля. В двоичной системе (дополнительный код) диапазон асимметричен (напр., от -128 до +127). В сбалансированной троичной системе $N$-тритное целое число покрывает $-\frac{3^N-1}{2} \dots +\frac{3^N-1}{2}$.
2.  **Эффективность округления**: Округление до ближайшего целого эквивалентно усечению. $0.5$ не может быть точно представлено, что позволяет избежать "проблемы округления 0.5".
3.  **Экономичность основания**: Экономичность основания $E(r, N) = r \lfloor \log_r N \rfloor$ минимизируется, когда $r = e \approx 2.718$. Целое число $3$ ближе к $e$, чем $2$, что делает троичную систему теоретически более эффективной для плотности хранения информации.
4.  **Знаковое представление**: Отрицательные числа не требуют отдельного бита знака. Знак несет старший ненулевой трит.

### 2.2.2 Реализация
В кодовой базе C++ триты симулируются на двоичном оборудовании для эффективности.
*   **Упакованное хранение**: `T81Int` использует схему кодирования 2 бита на трит (00=0, 01=1, 11=-1/T). Это позволяет поместить 4 трита в байт (один Трайт).
*   **Арифметика**: Операции реализованы с использованием целочисленной математики, которая симулирует цепочки переносов сбалансированной троичной системы.
    *   Пример: $1 + 1 = 1T$ (что есть $3 - 1 = 2$).
    *   Пример: $T + T = T1$ (что есть $-3 + 1 = -2$).

## 2.3 Аудируемость и трассировка Axion

**Статус: Реализовано и протестировано**

Детерминизма самого по себе недостаточно; выполнение должно быть **аудируемым**. Ядро Axion создает криптографический журнал, называемый **Трассой** (Trace).

### 2.3.1 Структура трассы
Трасса $\mathcal{T}$ — это упорядоченная последовательность событий $E_0, E_1, \dots, E_k$. Каждое событие фиксирует значимый переход состояния или проверку политики.

```cpp
struct AxionEvent {
    uint64_t tick;          // Логическая временная метка
    Opcode op;              // Попытка выполнения опкода
    Verdict verdict;        // Решение ядра (Allow/Deny)
    CanonHash81 state_hash; // Корневой хэш Меркла состояния VM
    std::string metadata;   // Контекстная отладочная информация
};
```

Эта трасса служит **Доказательством выполнения**. Проигрывая трассу относительно начального состояния, аудитор может математически доказать, что вычисление дало заявленный результат, не доверяя оборудованию, которое его произвело.

## 2.4 Девять принципов (Этический контроль)

**Статус: Реализовано и протестировано**

T81 встраивает набор неизменяемых "Конституционных принципов" ($\Theta_1 \dots \Theta_9$) непосредственно в движок политик VM. Это не просто рекомендации; это ограничения времени выполнения, обеспечиваемые Ядром Axion.

| Символ | Принцип | Описание | Кто обеспечивает |
| :--- | :--- | :--- | :--- |
| $\Theta_1$ | **Ненанесение вреда** | Фундаментальный слой безопасности; предотвращает повреждение памяти и segfault. | Проверки границ памяти |
| $\Theta_2$ | **Непринуждение** | Предотвращает принудительные переходы состояний без криптографической авторизации. | Проверка подписи |
| $\Theta_3$ | **Истина** | Информация должна быть канонической; два разных хэша не могут указывать на один и тот же объект. | Проверки коллизий CanonFS |
| $\Theta_4$ | **Интерпретируемость** | Предупреждение о непрозрачном выполнении "черного ящика"; генерация трасс обязательна для Уровня 3+. | Регистратор трасс |
| $\Theta_5$ | **Целостность идентичности** | Распределенные узлы должны поддерживать согласованные ключи идентичности. | Рукопожатие Уровня 4 |
| $\Theta_6$ | **Этический приоритет** | Политики безопасности имеют приоритет над оптимизацией производительности. | Вытеснение политик |
| $\Theta_7$ | **Сдерживание энтропии** | Предотвращает неограниченное расширение ресурсов (напр., бесконечные циклы, утечки памяти). | Лимиты рекурсии / Газ |
| $\Theta_8$ | **Каноническая согласованность** | Все данные должны быть нормализованы перед хэшированием. | Сериализатор |
| $\Theta_9$ | **Прозрачное выполнение** | Система не должна скрывать побочные эффекты; `MetaWrite` требует явного разрешения политики. | Перехватчик Axion |

> **Пример**: Если программа пытается уйти в бесконечную рекурсию, она нарушает $\Theta_7$ (Сдерживание энтропии). Ядро Axion обнаруживает, что `recursion_depth > policy.max_depth`, и выдает вердикт `Deny`, преобразуя операцию в `Trap::SecurityFault`.
