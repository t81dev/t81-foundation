# CanonFS portable identity and storage mapping audit

2026-10-22. Base: `0005ab675d2729b2795200e8c78ded43d4520b0d`, latest main.
PRs #554 and #536 remain open and unmerged. Native CI evidence is pending; local
ARM64 observations alone are not a Windows/Linux portability claim.

## Trace and compatibility decision

`write_object(type, bytes)` computes `hash_bytes(bytes)` in the existing persistent
driver. `vm/tracing/canonhash81.cpp` takes the first 32 bytes of SHA3-512; type
is metadata. `CanonHash81::to_string()` calls the canonical Base81 encoder in
`codec/base81.cpp`. The legacy driver concatenates that UTF-8 display string with
`.blk` or `.cap` beneath `objects/` and `caps/`. It creates files with exclusive
`open` or narrow `_open`; cold retrieval reconstructs the same path, reads bytes
and normally recomputes identity. Its cache can serve previously verified bytes
instead of observing a later on-disk mutation; the diagnostic environment can
disable legacy verification. Duplicate EEXIST currently returns a reference
without validating the existing bytes. Those legacy behaviors are preserved,
not represented as new v2 guarantees.

RFC-0054's implementation record and supplemental §§7.1/16/18 make the legacy
layout part of the release contract. Replacing the default would be breaking.
The correction therefore adds a separate versioned factory/root and a bijective
storage-key mapping; it does not change the current default or convert a store.
See the [compatibility RFC](../../spec/rfcs/RFC-00D6-canonfs-portable-storage-mapping.md).
Existing roots without the newly reserved marker remain on the legacy path.

## Filesystem audit

| Concern | Legacy exposure | V2 boundary |
| --- | --- | --- |
| Reserved characters | Alphabet includes ASCII `<` and `>` | Only 64 lowercase hex digits plus fixed safe suffixes |
| Reserved devices | Typed digests can display as `CON`, `NUL`, `PRN`, `AUX`, `COM1`, etc. | Every stem has 64 characters; cannot equal a reserved device stem |
| Case folding | `A` and `a` encode different supported digests but can alias as paths | One lowercase spelling per digest; uppercase keys/foreign filenames rejected |
| Unicode normalization | Base81 includes multibyte symbols; e.g. canonical decomposition of `≠` contains combining overlay | ASCII key is invariant under NFC/NFD; native case/normalization probes recorded |
| Trailing dot/space | Not generated by the canonical alphabet, but malformed external filenames can alias on Win32 | Strict key grammar rejects them; no display text is used as path input |
| Traversal/ADS | Typed digests, not arbitrary path strings, reach the driver; caller text parsing is separate | No slash, backslash, colon, NUL, root/prefix or dot components accepted in keys |
| Length | 32-byte digest displays in at most 41 Base81 codepoints, with variable UTF-8 byte length | Longest mapped component 72 ASCII chars; caller-root and full-path limits remain OS-dependent, without truncation |
| Encoding | Windows legacy `_open` uses narrow paths | V2 `_wopen`, `MoveFileExW` and native filesystem path streams; Unicode roots tested |
| Links/mixed versions | Legacy format has no marker/strict managed namespace | V2 rejects managed symlinks/reparse points, malformed entries, incomplete/unknown markers and mixed root directories |

Microsoft documents reserved characters, device names, case and trailing-dot/space
rules in [Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).
Apple's [APFS implementation notes](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html)
describe preserved names with case/normalization-insensitive lookup variants.
The audit measures each native filesystem rather than inferring its behavior
solely from the OS. Namespace checks assume an exclusively owned, serialized root;
they do not claim resistance to concurrent hostile ancestor/namespace replacement.

The strict new key parser does not change the global Base81 parser. Its existing
empty/NUL-padding/text-alias behavior and the fixed `to_text()` wire buffer are
separate surfaces, not alternate accepted v2 storage keys. No broad parser/wire
migration is smuggled into a filename correction.

## Original evidence and reproduction method

`original-554/windows-failure.tar.gz` retains the exact archived failed Windows
run from #554. `replay.py` verifies its SHA-256, selects the 110 completed B records,
and extracts their exact PO/evidence payload bytes to replay the corresponding
A storage transactions. Policy/VM execution is not reimplemented: this isolates
the protected write and evidence-archive stages responsible for the original
storage errors. If the PO write fails, archival is not attempted, matching the
original stage order. Every trial gets a fresh store; no invalid filename is
renamed or skipped. Hash and Base81 expectations are recomputed independently
with Python hashlib/integer arithmetic; actual native file bytes are inspected.
All original 100 failed trial IDs must fail again under the legacy factory on
native Windows, and all 110 must complete under the portable factory.

## Safety and remaining scope

V2 stages privately, closes, then publishes objects without replacement. Exact
existing bytes/hash must match before duplicate insertion succeeds. Corrupt or
partial final files are retained and rejected. Stale staging remains non-readable
and blocks new publication of that key. Strict masks persist with the same key
mapping. No policy semantics, signed capabilities, VM/ISA/numerical behavior or
cryptographic identities change. POSIX uses same-filesystem link/unlink; Windows
uses a wide move without replacement. No power-loss fsync, shared-writer safety,
transactional execution receipt, or arbitrary-long-root guarantee is claimed.

No legacy-to-v2 migration is implemented or required. Old binaries must not open
v2 roots; newly compiled legacy factory calls refuse their reserved marker. A
wrong old writer can create mixed directories; the v2 reader then refuses rather
than falling back to a different authorization namespace. Roots already using the
new reserved marker name require operator review. Default CLI/import/export remain
legacy-only, preserving RFC-00D1 result/provenance fixtures. Default switching or
any copy-migration/cutover needs separately approved compatibility work.


## First native run: retained audit failures

At source `3ceee34477003482526209f61e26c9ab51568ace`, native Linux x86_64 and
macOS ARM64 passed both the corpus and six legacy suites. Native Windows built,
reproduced 100 legacy storage failures and completed all 110 portable transactions,
but the expanded audit failed on two assumptions. Its
[complete first Windows artifact](observed-initial/windows.tar.gz) is retained.

First, a successful Win32 stream open of `CON.blk` can refer to a device without
creating a directory entry. Requiring a format validator to reject an entry that
was never created is incorrect. The corrected test enumerates actual entries and
records stream-open and directory-entry outcomes separately. It still rejects
all malformed keys and any invalid entry that is actually present; it does not
skip the reserved-name observation.

Second, the ten remaining legacy API-success cases use code-page-dependent
mojibake filenames on this Windows host. The original narrow `_open` interprets
UTF-8 display bytes through its native ANSI code page. The audit retains these
additional filename mismatches as failures of portable representation, separate
from the 100 original creation errors. The corrected observer independently
computes the exact legacy spelling using native `GetACP()`, validates the entire
file inventory and payload, and also records whether that spelling equals the
canonical Base81 display. It never reports a noncanonical legacy path as a
portable success. V2 remains subject to exact canonical-hex path and byte checks
on every host. This distinction is necessary to reproduce the original write/read
criteria without erasing the stronger audit's new encoding finding.
